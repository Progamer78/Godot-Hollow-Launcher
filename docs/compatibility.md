# Current limits and remaining work

Latest update: the unchanged Captive Lili PCK now starts for 180 frames in a compiled Windows 4.7.2 runtime, headless and OpenGL, without script errors. Legacy tokenizer v100 is read with header/token translation; v101 remains supported, and unknown versions are rejected during inspection. LimboAI 1.8.1 is statically bundled, not loaded from the game. Godot 3 also bundles Spine 4.2. Live stats/cheats and a Godot expression console run through the shared PlayerTools module; 48 native checks pass in each desktop engine. Anomalous Coffee Machine's 96 encrypted scripts still require a matching export key/unencrypted export. See [detailed validation and limitations](game-tools.md). The new iOS code/IPA has not been compiled or run here.

The user reports the Godot 4 player, floating menu, Spine and editable controls working on iPhone. This update adds Godot 3 integration, joysticks and portrait fitting. Its new native code has not yet been compiled on macOS or device-tested.

The first adapter targets complete, unencrypted Godot 4 GDScript packs. Header metadata suggests a candidate runtime; it cannot prove rendering, bytecode, assets, API, autoload, or scene compatibility. A 4.7.2 runtime may fail older 4.x exports despite accepting their headers. Versions newer than 4.7 are rejected. Godot 3 selects the separate bundled 3.6.3 framework; native compilation and device execution of that adapter are pending. The manual override selects among known adapters and never overrides an unsupported engine major.

The inspector supports pack-directory formats 1–4, separates format and engine versions, validates bounded directory reads, paths, offsets, settings signatures and resource bounds, and rejects encrypted/sparse/delta/removal archives and .NET source. Native descriptors/libraries produce a warning and require the explicit “Try without native extensions” option before Play. Native loading remains blocked at the engine boundary. Optional extensions may be unused during offline play; required native classes can still prevent startup. Asset payload checksums and dependency completeness are not exhaustively checked. Encrypted scripts, external resource bundles, Windows native APIs, C#, GDNative and executable GDExtensions remain unsupported.

The build now includes the official Spine C++ module by default (4.2), with immutable source revisions and preserved separate licensing. This is a trusted dependency compiled into the application, not permission to load native libraries from a PCK. Only one Spine minor version is currently compiled into an IPA. Versions 4.1 and 4.3 are selectable build options, but have not been tested here.

The initial Spine integration failed compilation because its C++ module expected older Godot headers/APIs. Staging now adapts callable/rendering/scene-tree includes, rendering enum/type namespaces, animation-library iteration, JSON ownership and loader/saver references for Godot 4.7. The animation-data version stays Spine 4.2, and the upstream checkout is unchanged. The adapted 100-file module and full Godot 4.7.2 Windows runtime compile successfully with Clang. The unchanged Goodbye Eternity Mac PCK starts for 90 headless frames, exit 0 and zero script errors; certificate-store and shutdown-leak messages remain. Rendering and gameplay are not established by this test. The user subsequently built the corrected Godot 4/Spine IPA and reports it working. These historical local checks do not verify the new dual-runtime update.

Goodbye Eternity 0.14.1's Windows and Mac packs contain Godot 4.6.1 metadata and Spine 4.2.38–4.2.43 skeletons. Standard Godot reproduces the supplied missing-class/splash-scene failure. Both unchanged packs start headlessly in the official Spine 4.2-enabled Godot 4.6.1 desktop build without script errors. The preceding Godot 4/Spine update was built by the user and is reported working on iPhone. Full gameplay, iPhone rendering and memory use of this 2.19 GB PCK remain unverified. The logs show a missing dependency, not an out-of-memory failure. GPU texture conversion warnings may still affect memory/performance after that dependency is present.

Metal and OpenGL ES are compiled. The supplied logs show both Compatibility and Mobile renderers working on iPhone. Explicit Vulkan-only settings, platform-specific textures, unsupported codecs, plugins, and desktop shader assumptions may require a compatible game export; there is no automatic asset conversion.

The official Godot controller/keyboard/touch paths are retained. Virtual buttons emit key press/release events, including modifiers and physical key codes. Per-game layouts, keyboard/mouse mappings, saved visibility, and mouse movement/clicking are implemented and user-reported working. Built-in cursor shapes currently share the default arrow. The collapsed movable menu is user-reported working; its gestures are attached to the 44-point handle before positioning, avoiding an invisible screen-sized drag target. Audio focus, rotation and safe-area edge cases still need dedicated tests. Fixed/floating virtual sticks emit configurable keyboard directions, including diagonals; they do not emit analog gamepad axes. The new stick and portrait-fit UI await native compilation and device tests. Virtual gamepad buttons, diagnostics toggles and FPS UI remain unimplemented. Godot 3 uses the default virtual cursor arrow; custom Godot 3 cursor images are not exposed through the bridge yet.

Pokémon Battle Advanced 0.3.3 includes a native WebRTC descriptor with no iOS library. Its scripts initialize the connection backend only when using host/join. The original pack reaches its boot scene on Windows 4.7.2 without that backend and without script parse errors. Full gameplay and iPhone startup remain unverified; online WebRTC will not work in this build.

Per-game `user://` isolation is implemented for ordinary save APIs, including games with identical project names. It has not been device-tested. It is **not a security boundary between imported scripts**: ordinary GDScript can access other app-sandbox files by absolute path and can use network APIs when connectivity exists. iOS provides the app sandbox; this project does not implement a separate script sandbox. Import trusted games only. No online service is required to play.

There is one engine lifetime per process. After a launch attempt or engine setup failure, close and reopen the app. Main-scene startup failures are now checked using the actual `Main::start()` return status, rather than only the main-loop pointer; the alert includes a bounded log-based Spine hint when available. Returning to a running library, launching another engine in-process, crash recovery, and reliable engine teardown need further investigation. Logs created after Godot's file logger starts are in the UUID save directory; earlier initialization failures may only appear in the Xcode/device console.

## Godot 3 adapter status

The implementation and CI steps are included; see [Godot 3 details](godot3.md). The unchanged Sadiubus PCK (Godot 3.4.2 metadata) started in official Windows Godot 3.6.3, exit 0, no script errors. An original Godot 3 PCK ran twice for 90 frames with input, animation and save-reload checks. These tests use the official desktop engine, not the new iOS adapter.

The supplied ARM64 templates share 18,264 defined external symbols. Godot 3 is therefore linked as an isolated framework, not into Godot 4's executable. Its public export list contains only `GP3GetAPI`; engine-owned Objective-C classes/protocols receive a `GP3` prefix. Packaging audits framework exports, Objective-C metadata, and host/guest registration collisions. The framework is bundled at build time and must be signed with the app. It is loaded only when a Godot 3 game is selected, and never unloaded.

Remaining acceptance work: compile/link/sign the new ARM64 framework and launcher through Actions, then cold-launch the original Godot 3 test PCK and Sadiubus and a Godot 4 game in the same installed IPA. Verify input, portrait rotation, touch coordinates, audio focus, saves, lifecycle and signing on-device. No multi-version device result is claimed yet. Godot 3 and Godot 4 each retain one engine lifetime per process.
