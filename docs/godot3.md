# Godot 3 integration

The latest combined compatibility/cheats package also builds Spine 4.2 and the shared PlayerTools module into this runtime. The complete Windows 3.6.3 release engine compiled and starts the original Sadiubus PCK; 48 native tools checks pass. The iOS framework/adapter still needs Actions and device validation. See [current update](game-tools.md), including the encryption blocker for Anomalous Coffee Machine.

The new implementation targets official **3.6.3-stable**, commit `a3378686f7196db78d7b3cc7947f72a13bc4864c`, alongside the working Godot 4.7.2 image. Godot 3.6.3 is the stable maintenance release selected from the [official releases](https://github.com/godotengine/godot/releases/tag/3.6.3-stable). The [official iOS compilation flow](https://docs.godotengine.org/en/3.6/development/compiling/compiling_for_ios.html) and supplied template use `platform=iphone target=release tools=no arch=arm64` and native OpenGL ES rendering.

## What was inspected and tested

- The supplied 3.6.3 iOS template: Xcode project, entry-point structure, framework links, Info.plist and release ARM64 static archive. It requires iOS 15. The supplied 4.7.2 archive was retained for comparison. LLVM's Mach-O symbol inspection found **18,264 shared defined external symbols** between the ordinary engine archives, supporting the decision to keep separate images. There were no shared defined Objective-C class symbols in these particular templates; all Godot 3 classes/protocols are nevertheless prefixed to keep runtime registration private to that engine.
- Sadiubus: the original `Sadiubus_x64.pck` has format 1, Godot **3.4.2** metadata, 1,927 entries, 69,863,344 bytes. The extracted project declares a 768×432 canvas with 2D/keep stretch. Original scripts/scenes/autoloads were inspected, not rewritten. The original PCK ran with official Windows 3.6.3, GLES2, `--main-pack --no-window --quit`: exit 0, no script errors. This verifies startup, not complete gameplay.
- `samples/godot3` is an original small game. It was exported with the official editor to an independent PCK, run from an empty directory for 90 frames twice, and verified keyboard input, animation and save reload. Save counters were 0 then 1. Runtime/asset downloads were SHA256-verified against official release metadata. Windows test save paths are inside `build/godot3-proof/`.
- Seven Python tests pass, including both engine patchers against actual official source, preservation of the working export process, legacy-script/LimboAI staging, and a framework collision-check fixture. These are source/build-helper checks, **not an ARM64 compile**. New Swift tests for migration, joystick mappings/persistence, portrait fitting and tools transport are included for CI; they cannot run in this Windows environment.

The new iOS adapter/framework and Swift UI have **not yet compiled or run here**. No new IPA was produced locally. Full multi-version iPhone support is not established until both engines launch independent imported games in the same signed application.

## How the engines are separated

Godot 4 stays linked as before. Godot 3 is compiled as `Godot3Runtime.framework`, with hidden engine symbols and a single export, `GP3GetAPI`. The versioned bridge in `ios/Godot3API.h` contains UIKit/Foundation objects and plain values, never Godot/C++ objects. The framework uses Mach-O two-level namespaces. Seventeen source-level Objective-C class/protocol names receive `GP3` prefixes, including forward declarations and protocol references. The linker/packaging helpers audit actual exports and Objective-C metadata and reject overlapping host/guest definitions.

The app uses `dlopen` only for that exact bundled framework path after selecting a Godot 3 pack. This is trusted native code shipped and signed with the IPA. Imported native libraries are blocked at Godot 3's OS boundary, and its GDNative module is disabled. Godot 4 retains its existing native-extension block. The framework remains loaded until process exit; selecting another game or engine requires closing/reopening the app.

The adapter reuses upstream `iphone_main`, project setup, view controller, GLES layer, renderer, audio and controller handling. It supplies the validated external `--main-pack` before initialization and passes the UUID save directory as the runtime's data directory. It ignores dummy export arguments, keeps the SwiftUI host's window, forwards lifecycle notifications, and checks actual `Main::start()` success. Key and mouse events are translated through Godot 3's own input types. Virtual mouse modes and query state are implemented; the software cursor uses the standard arrow.

## Build and installation

The existing Actions workflow now checks out both pinned engines, exports/tests a Godot 3 proof PCK, type-checks the launcher, builds the Godot 3 iOS adapter archive first, then its complete engine/framework. It subsequently runs the existing Godot 4/Spine build, reference export/Xcode archive and IPA packaging. The built Godot 3 framework and its original MIT/third-party notices are copied into `Payload/player.app/Frameworks` before packaging. The artifact includes per-engine build logs and proof packs.

1. Upload the update ZIP's folders at your existing repository root, including the new **runtime3** folder, **bootstrap/export_presets.cfg**, and updated **.github/workflows/ios-player.yml**.
2. Run **Actions → Build native Godot Player**, Spine **4.2**. Download **GodotPlayer-build-and-tests** and extract `GodotPlayer-unsigned.ipa`.
3. Sign the IPA with the same app identifier and personal signing identity as before. The signing tool must sign `Frameworks/Godot3Runtime.framework` and the app. Install as an update; avoid uninstalling if you want to preserve saves.
4. Verify your working Godot 4 games first. Close/reopen the app, import the artifact's `godot3.pck`, and Play. Close/reopen, import the untouched `Sadiubus_x64.pck`, and Play. Use automatic runtime selection. Try GLES2 if a game's default GLES3 renderer is incompatible.
5. Verify game audio, original keyboard/controller/touch behavior, save reload, background/foreground and rotation. Logs are in Files → Godot Player → GodotPlayerSaves → game UUID → `player.log`.
6. Add a fixed joystick, set direction keys, Apply and Save; close/reopen and confirm persistence. Switch it to Floating, drag at different locations, press other buttons concurrently, and verify releases after lifting a finger/backgrounding. Mouse mode changes it back to fixed. Portrait · Fit should show the entire scene and preserve correct click/touch positions.

For a manual macOS build, use the workflow's exact commands. The Godot 3 steps are `patch_godot3.py`, `scons platform=iphone target=release tools=no arch=arm64 module_arkit_enabled=no module_camera_enabled=no module_gdnative_enabled=no lto=none optimize=size 'CCFLAGS=-fvisibility=hidden -fvisibility-inlines-hidden'`, then `build_godot3_framework.py ENGINE build/runtime3`. Add the resulting framework to the generated Xcode app target with **Embed & Sign** before Product → Run/Archive. The Actions path embeds it after the unsigned archive instead. Only ARM64 iPhone builds are integrated; simulator support is not included.

Godot 3 games requiring Mono, GDNative, missing resources, platform-specific textures/codecs or custom engine modules can still fail. The keyboard joystick has eight directional states and a configurable radial deadzone; it is not an analog gamepad-axis implementation. Separate engine lifetimes, full gameplay compatibility, automatic asset conversion and script sandboxing are not promised.
